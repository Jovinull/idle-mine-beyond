# Saves, time, and offline progression

## Legacy save behavior observed in source

Scripts/Define/functions.js stores the save under localStorage key IdleMine. It serializes the game object as JSON, applies encodeURIComponent and escape, then Base64-encodes it. Import reverses Base64, decodeURIComponent, and unescape before JSON parsing. Base64 is encoding, not encryption.

The pinned current save shape and a deliberately minimal partial-save load are captured in `saveSemantics` in the reference corpus. The current serialized object has 27 top-level fields and no version field; nested settings, story, upgrade groups, Powers, and pickaxe keys are recorded in the fixture. Seven Decimal resource values serialize as strings, and JSON omits upgrade `getPrice`/`getEffect` functions. This describes the captured current runtime, not every historical save.

The probe confirms the source's exact encode/decode order and a Unicode corruption on round-trip. See the dedicated legacy quirk entry; preserve the observed behavior while parity is the goal. `loadGame()` performs field-by-field assignment rather than schema validation or a versioned migration. In the synthetic `{ "story": {} }` case, missing resource values become Decimal zero, Story fields take their defaults, absent Gem and Planet Coin upgrade groups reset their levels to zero, and absent settings, Money upgrades, Powers, and pickaxe leave seeded runtime values in place. This single controlled case is evidence for those branches, not a complete catalog of old-save variants or corrupt-input behavior.

The separate `saveApplicationSemantics` capture loads a complete distinct save with offline processing disabled. It verifies all seven resource fields, progress and regenerated current object, Story fields and scroll position, `lastActive`, number formatter, theme/toggles, all four upgrade families, five named Powers values, and pickaxe fields. `settings.tab` is serialized but not read by `loadGame()`; the existing tab remains active. The load reads the clock for the `lastActive` fallback even when the save supplies that timestamp. `timer`, `usedGemsLevel`, and other serialized runtime/presentation fields are not assigned by this loader.

`saveOfflineApplicationSemantics` captures one controlled wrapped save loaded through the pinned `loadGame()` with offline processing enabled. The save selects a generated object, pickaxe, Powers, upgrade levels, notation, and 3,601 seconds away; the probe records live Money/Gem/Planet Coin rates, final resources and maxima, Story/settings/pickaxe state, clock values, and the post-reward storage snapshot. The exact event order is theme application → offline reward message → storage write → `Game Saved!`. Four clock reads are observed: eager `lastActive` fallback, elapsed-time calculation, updated `lastActive`, and `saveGame()` timestamp.

Absent and empty groups have distinct source behavior. Missing `upgrades` preserves existing Money upgrade levels; missing `gemUpgrades` and `planetCoinUpgrades` reset their families to zero; missing `powers` preserves power values and Wisdom upgrades. A present `powers` group with no `upgrades` resets Wisdom upgrade levels, while an empty `powers.data.values` leaves existing values unchanged. A missing `pickaxe` preserves it, while `{}` sets its name to `Toy Pickaxe` and its Decimal power and quality to zero because `new Decimal(undefined)` runs before the apparent fallback. A present empty `settings` group defaults the formatter index to zero, theme to light, and both toggles to false. These behaviors are captured in `saveSemantics.missingOptionalGroups`, `saveSemantics.emptyPresentGroups`, and `saveApplicationSemantics`.

`packages/persistence` decodes the Remix wrapper and `applyRemixLegacySaveFields()` applies captured current-save fields to immutable core state. `loadRemixLegacySaveIntoState()` then composes offline rewards and returns ordered theme/log/save effects. It passes the eager timestamp fallback read into the core offline action, preserving the four-clock-call combined path without duplicating a read, and resolves the loaded number formatter only when a reward message is produced. Its save effect contains the full application state at the source save point.

The package also defines a strict, versioned Beyond v1 JSON envelope. It stores every mutable field in `RemixLegacySaveApplicationState` as JSON-safe data, validates the shape and Decimal strings with Zod, rejects unknown fields and unsupported versions, and reconstructs the current mine object from its persisted object ID and the pinned catalog. This is a Beyond persistence contract, not a claim about Remix's versionless format; no older Beyond version exists to migrate yet.

`importRemixLegacySaveToBeyond()` applies the source-compatible loader, dispatches theme/offline effects in order, and writes the resulting v1 state under the separate Beyond key. It leaves `IdleMine` untouched. If the legacy load has a source save effect, `Game Saved!` is dispatched only after the primary write succeeds. A successful import without offline rewards is persisted silently because Remix produced no save effect. The browser adapter stores the previous valid primary as one backup generation, preserves a valid backup when the current primary is corrupt, and reports backup recovery without silently rewriting either value. It refuses to load a backup over or overwrite an unsupported future version. Native storage, UI wiring, export controls, and recovery UI remain open.

Additional controlled source cases distinguish an absent group from a present-but-empty group and capture the failure order for empty Base64, invalid Base64, invalid percent escapes, Base64 containing invalid JSON, and a parsed save without `story`. Separate source cases confirm that `atob` accepts ASCII whitespace and omitted Base64 padding. See `saveSemantics.emptyPresentGroups`, `saveSemantics.base64Variants`, and `saveSemantics.loadErrors`; these are representative branches, not a complete historical-save or recovery catalog.

The hard-reset implementation calls localStorage.clear(), which clears all origin storage rather than only this game's key. This is source-observed; its impact depends on the hosting origin.

## Offline progression observed in source

**Verified legacy behavior (pinned source and controlled runtime):** `functions.loadGame()` evaluates its `Date.now()` fallback while reading `lastActive`, then reads the clock again for elapsed time even when the save already has a timestamp. Rewards apply only when elapsed time is strictly greater than 300 seconds and `nooffline` is false. In that branch it obtains Money, Gem, and Planet Coin rates from `getMPS()`, `getGPS()`, and `getPCPS()` using the loaded current object, pickaxe, Powers, upgrades, and highest-damageable scan. The offline duration is `Math.min(3600 * (6 + Offline Time effect), elapsedSeconds)`. Money is `MPS × (0.5 × duration)`; Gems and Planet Coins are `floor(rate × upgrade effect × duration)`, with their respective offline-upgrade effects. On apply, Remix logs a return message, updates resources and their maxima, reads `Date.now()` for `lastActive`, then `saveGame()` reads it again before storing the save. A controlled advancing-clock case captures these separate reads.

Ten cases in `offlineProgressionSemantics` cover missing timestamps, the exact and just-over 300-second boundary, exact/over default cap, an upgraded cap, the explicit `nooffline` flag, negative elapsed time, zero rates, and clock movement between reward calculation and save. They capture log and save ordering, resources, maxima, stored state, and formatter output. The probe stubs MPS/GPS/PCPS to isolate the offline-load branch; it does not validate every live state that generates those rates. Manual import in `index.html` calls `loadGame(saveString)` without a `nooffline` argument, so it follows the same offline check; hard reset explicitly passes `true`.

`packages/core/src/remix-offline-progression.ts` reproduces the pure resource/timer transition with an injected clock, offline rates, upgrade effects, and number formatter. Its rate source can be resolved lazily after the threshold check, preserving the legacy ordering. `performRemixSimulationAction()` supplies a lazy rate resolver that uses the loaded state and catalog, shares the mining action's factor/highest-damageable calculation, and then calls the same source-backed MPS/GPS/PCPS formulas. Nine captured formula states are exercised through this full action, including low-damage boundaries, a last-damageable-object Gem bonus, an extreme object ID, and zero-damage cases. Four additional browser captures call real `loadGame()` with controlled saves and real rate functions; Vitest compares rates, rewards, saved resources, clock reads, log text, and stored snapshots. The source emits `Game Saved!` after a successful storage write. The web persistence service now emits this exact confirmation after its versioned primary write, and the legacy-import coordinator preserves theme → offline message → write → confirmation order. Core save effects from regular simulation actions are not wired into this coordinator yet. Ten isolated offline branch fixtures continue to cover timing, caps, multipliers, and save order with controlled rates. This is not a complete save or app integration. Most legacy field defaults and variants, recoverable corrupt inputs, alternate notation output, and the visual return message remain open.

## Main simulation time and autosave timer

**Verified source and controlled frame behavior:** `Scripts/main.js` reads `Date.now()` to compute a delta at the start of each `requestAnimationFrame` update, then reads it again to set the next baseline. It increments the auto-pickaxe and save timers by the same delta. The auto timer performs at most one hit and resets to zero when strictly over its interval. The save timer saves once and resets to zero only when strictly over 60 seconds; exact equality does not save, and long-frame excess is discarded. Every update requests story-notification refresh after the save check. The ten hit plus four frame cases in `miningHitSemantics` cover these timer boundaries and event order.

**Verified source behavior:** `Scripts/upgrade.js` `Upgrade.buy()` updates the selected currency and upgrade level without calling `saveGame()`. The canonical upgrade definitions in `Scripts/Define/game.js` provide no custom `onBuy` hooks. An upgrade purchase therefore has no immediate persistence effect; a controlled close/reopen before the next periodic save is not currently fixture-covered.

**Verified legacy behavior (pinned source and controlled runtime):** `index.html` passes `functions.getUsedGems()` into `functions.craftPick()`. Crafting saves immediately after each strictly stronger pickaxe replacement, after the replacement log event. A Shift bulk action can therefore emit multiple saves containing distinct intermediate Gem balances and equipped pickaxes. Duds and attempts without enough Gems do not save. `pickaxeCraftingSemantics` captures a two-replacement case with successive snapshots at 3 Gems / `Bad Mud Pick` and 0 Gems / `Sturdy Mud Pick`; the composed core action preserves each snapshot as an ordered save effect. This is a core-state snapshot, not a complete legacy save serialization or persistence adapter.

Beyond's `advanceRemixSaveTimer` reproduces the strict threshold/reset, and `performRemixMiningAction` returns ordered frame events for save and story refresh. A browser/native adapter must still execute those events against persistence and the story transition. The current captures supply elapsed delta directly; behavior of the two separate `Date.now()` reads under a changing system clock remains source-observed but unprobed. Rendering cadence affects automatic hit counts under long frames. Keep the clock injected and do not change outcomes during parity without an accepted exception.

## Beyond architecture decision

- Save schema is versioned and validated; migrations, integrity checks beyond strict schema/Decimal validation, backups, safe recovery, import/export, and a legacy Remix importer remain required.
- Browser and native storage are adapters; the core never imports localStorage, IndexedDB, filesystem, or Tauri APIs.
- Clock/time is injected. No direct Date.now() in simulation code.
- Legacy RNG is injected. No casual Math.random() in game-domain code.
- New persistence must not silently replace legacy data before a successful import.

The current persistence package implements the legacy codec, current-save field application, pure offline-load orchestration, the Beyond v1 schema, backup-aware storage coordination, and legacy-load migration. The browser adapter is implemented but is not wired into the app UI or regular simulation save effects; native storage, recovery UI, and complete legacy save compatibility remain open.

`tests/parity/save-format.test.ts` checks source shape, encoding order, Unicode round-trip result, and the minimal missing-groups case. `tests/parity/legacy-save-application.test.ts` compares captured field application and absent/empty group behavior; `tests/parity/legacy-save-offline-application.test.ts` compares the wrapped save, live-rate offline rewards, no-offline branch, exact clock count, effect order, and save snapshot, then round-trips the captured post-reward state through Beyond v1. `tests/parity/beyond-save.test.ts` round-trips all v1 state fields, extreme Decimal values, and a derived object ID, and rejects malformed JSON, unsupported versions, invalid Decimal strings, and extra fields. `tests/parity/remix-beyond-save-storage.test.ts` covers write order, backup retention, malformed recovery, newer-version protection, browser key separation, and the captured legacy-import effect order. UI wiring, native storage, export controls, and recovery UI remain open.
