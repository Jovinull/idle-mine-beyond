# Criticisms and community reports

This document preserves observations and player reports recorded in the bootstrap research. They are research leads, not permission to alter Remix behavior. The source dossier did not include stable direct links for each quoted report, so these summaries are **unverified community reports** unless independently sourced later.

| Topic                 | Report or criticism recorded                                                                                                                                              | Compatibility handling                                                                                         | Possible post-parity work                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Gem grind             | Players report long stretches where gems dominate progression and money has little use; the original research notes that the developer acknowledged this as a weak point. | Preserve drop rules, costs, and pacing during parity. Verify exact behavior against source/runtime.            | Measure resource dead zones, gem income, sinks, and mid/late money utility.                                                     |
| Dud crafts            | Players report frustration at spending many gems on weak/dud results; others describe high rolls as memorable and exciting.                                               | Preserve random distributions, duds, costs, and replacement conditions exactly.                                | Evaluate probability displays, craft history, bulk-craft feedback, discard controls, and extremely gentle pity only if desired. |
| External autoclickers | Reports say high click rates accelerate active-power progression and can reward external automation.                                                                      | Preserve click-triggered behavior during parity; do not silently normalize input rates.                        | Consider built-in repeat/hold, active upgrades, or rate normalization.                                                          |
| One-hit farming       | Players can prefer a lower mine object if it can be destroyed in one hit and gives a better expected drop rate than a more advanced object.                               | Preserve object selection, damage, drops, and Gem Bonus behavior. The best farm need not be the newest object. | Reassess resource-farming incentives only after compatibility.                                                                  |
| Story pacing          | Some players value the story; others describe repeated reach-the-next-object objectives with little immediate reward.                                                     | Preserve the complete original story, objective order, unlocks, and presentation.                              | Add clearer rewards or new story only after parity.                                                                             |
| Procedural endgame    | Reports describe post-Universe progression as increasingly abstract or less meaningful than procedural mineral progression.                                               | Preserve current endpoints and generated behavior, including the existing Universe boundary.                   | Investigate meaningful content beyond the compatibility endpoint.                                                               |
| Background progress   | Players report inconsistent background-tab and offline progress. Source code also shows requestAnimationFrame/timer behavior that merits controlled measurement.          | Match evidenced legacy outcomes. Distinguish visible reference behavior from internal code concerns.           | Separate simulation and rendering clocks and improve offline computation after parity.                                          |
| Lost or broken saves  | Reports describe lost saves and historical export/import problems around updates or browser/domain storage.                                                               | Extract load, reset, export, and import semantics into fixtures before implementation.                         | Add versioning, migration, validation, backups, safe recovery, and cross-platform persistence.                                  |

See [legacy quirks](legacy-quirks.md) for source-observed implementation concerns and [post-parity backlog](POST_PARITY_BACKLOG.md) for proposal tracking. Source/runtime behavior outranks these reports under the [evidence hierarchy](lineage.md).

When a report is independently verified, add a stable source link, date/context, and exact claim. Do not convert a reported problem into a compatibility exception without the complete documented process.
